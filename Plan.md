# Tenantcheck Implementation Plan

Ordered build plan for the MVP. Each phase should be shippable and testable on its own before moving to the next. See `product_spec.md` for the product spec and the architecture rationale (schema, RLS strategy, stack validation) that shaped this plan.

**Stack**: Next.js (App Router, TS, Tailwind) + Supabase (Postgres/Auth/Storage) + PayFast + Resend (email).

**Live project**: Supabase project `TenantChecker` (`wqodoiavjwuowfkkrmjp`, eu-west-1), linked via `supabase link`. Schema lives in `supabase/migrations/`.

Tenant now sees a passive "waiting on your landlord" message with no payment action.
- [x] PayFast ITN webhook (`/api/payfast/notify`) — verifies the signature, checks `payment_status = COMPLETE`, calls `mark_paid()` via a service-role client (`src/lib/supabase/service.ts`). - [x] Return/cancel pages (`/landlord/checks/[id]/pay/return`, `.../cancel`) plus a tenant check-status page; tenant dashboard shows a real to-do list (consent action only — payment is landlord-side).
- [x] **Six real bugs found and fixed via new migrations, all caught by actually driving the flow rather than by inspection** (the payment-gate persona mix-up above is a seventh, functional/requirements bug rather than a migration one):
  - `payments` and `properties` had zero RLS SELECT policies for tenants — the payment page (at the time still tenant-side) silently computed a R0.00 amount (payments row invisible under RLS) and PayFast rejected the form. Added tenant-scoped SELECT policies on both (kept after the move to landlord-side payment — harmless read access, and the tenant consent page still needs the property-label read).
  - `mark_paid()` called `log_audit()` with its arguments in the wrong order (`null` landed in the NOT NULL `action` column), so every real PayFast ITN silently 500'd. Only surfaced by completing an actual sandbox payment and watching the webhook fail.
  - A broader sweep: `consents.tenant_id`, `payments.landlord_id`, `application_forms.tenant_id`, and `documents.uploaded_by` all had the default `NO ACTION` delete behavior, blocking deletion of almost any real user (found while cleaning up test accounts). Changed to `ON DELETE SET NULL` (dropping `NOT NULL` where needed) — same reasoning as the earlier `audit_log`/`checks.shipped_by` fix: these records should survive account deletion, not block it.
- [x] Verified twice with genuine end-to-end runs — not mocked: real signup, real invite accept, real consent, a **real PayFast sandbox payment actually completed** (via a temporary Cloudflare quick tunnel so PayFast's servers could reach the local ITN webhook), confirmed the webhook fired and `mark_paid()` ran, check status advanced to `AWAITING_APPLICATION`, and both tenant and landlord UIs reflected it correctly. First run (11/11) was against the tenant-pays version before the correction; re-run (13/13) against the corrected landlord-pays flow, additionally asserting the tenant sees no payment action at all. Tunnel torn down and all test data cleaned up both times.

## Phase 7 — Notifications (email first) ✅ done

- [x] Wired Resend (`src/lib/resend.ts`) for transactional email. **Your call**: `RESEND_API_KEY` is deliberately left blank in `.env.local` for now — `sendEmail()` no-ops (logs a warning, returns `{ok:false}`, never throws) until a real key is added, so every trigger point below ships and is fully tested without live delivery being a blocker. Sender defaults to Resend's shared sandbox address (`onboarding@resend.dev`, your call) via `RESEND_FROM_ADDRESS` — swap for a verified domain before this can actually reach real tenants/landlords (added to the Phase 8 list).
- [x] `log_notification()` RPC (new migration) — mirrors `log_audit()`'s shape so server-side code can log a `notifications` row for whichever party is the *recipient*, not just the actor (e.g. a tenant's consent needs to notify the landlord), without opening `notifications` up to broad client-side INSERT policies.
- [x] Four trigger points, each firing from the same server-side code path as its RPC and wrapped so a notification failure never blocks the underlying action:
  - `consent_requested` → tenant, from `buyTenantcheck()` right after `create_check()`.
  - `payment_requested` → landlord, from `submitConsent()` right after `submit_consent()`.
  - `application_requested` → tenant, from the PayFast ITN webhook right after `mark_paid()`.
  - `check_completed` → landlord, from `shipCheck()` right after `ship_check()`.
  - Landlord's email isn't stored anywhere client-queryable (`profiles` has no email column; it lives on `auth.users`), so the two landlord-facing triggers use a new `getUserEmailById()` helper (`src/lib/supabase/service.ts`) via the admin API.
- [x] Stale-invite handling, built as **one Next.js route** (`GET /api/cron/process-expirations`, shared-secret-protected) rather than the originally-planned `pg_cron` job — deliberate deviation, noted here rather than silently: pairing `pg_cron` with `pg_net` to call out to an email provider would mean the Resend key has to live in Postgres config too (a second secret-storage surface), and pg_net calling `localhost` isn't reachable from Supabase's cloud Postgres without the same tunnel workaround Phase 3 needed for the PayFast webhook. Keeping it as one route keeps the key in one place and made it fully testable this session with no tunnel. `vercel.json` schedules it every 6h for when this deploys to Vercel. It reminds whoever needs to act next — the tenant while `AWAITING_CONSENT`, the **landlord** while `AWAITING_PAYMENT` (payment is landlord-side, per the Phase 3 correction) — once within 48h of their invite's expiry, deduplicated via a `notifications` lookup so re-running it never double-sends; then calls `expire_stale_checks()` (new `SECURITY DEFINER` RPC, `service_role`-only) to flip anything that blew through the deadline to `EXPIRED`.
- [x] **Real security bug found and fixed while testing, unrelated to this phase's own code but caught here**: `revoke execute on function ... from authenticated, anon` does not actually restrict a function to `service_role` — Postgres auto-grants `EXECUTE` to the `PUBLIC` pseudo-role on function creation, and `authenticated`/`anon` inherit from `PUBLIC` regardless of what's revoked from them individually. This affected both the new `expire_stale_checks()` *and* the original Phase 0 `mark_paid()`, meaning **any authenticated (or anonymous) client could call `mark_paid()` directly via the Supabase API and fraudulently mark any check as paid without ever going through PayFast** — live on production data until this was caught. Fixed via a new migration revoking from `public` specifically (which actually removes the grant); confirmed via `information_schema.role_routine_grants` that only `service_role`/`postgres` can execute either function now.
- [x] WhatsApp integration still deferred — revisit once email flow is stable and business verification (Twilio/Meta Cloud API) is in progress.
- [x] Verified end-to-end against the live Supabase project **and** the real running dev server. Coverage note: three of the four trigger points live inside Next.js Server Actions (`next/headers`-dependent, invoked over an internal RPC wire protocol not safely hand-replicated without a real browser, unavailable this session) — those are verified by code review plus a direct test that `log_notification()` accepts the exact row shapes each one produces. The fourth trigger point (the PayFast webhook) and the cron route are plain route handlers with no `next/headers` dependency, so those got full real-HTTP coverage: a **genuinely signed PayFast ITN POST** (same PHP-SDK-compatible signature algorithm as Phase 3) driving `mark_paid()` for real and confirming the resulting `application_requested` notification; `expire_stale_checks()` tested directly (a deliberately backdated invite flips to `EXPIRED` with an audit row, a fresh one is untouched, and — post-fix — a regular authenticated user is correctly blocked from calling it); and the cron route tested for both reminder branches (tenant recipient while `AWAITING_CONSENT`, landlord recipient while `AWAITING_PAYMENT`), auth rejection (missing/wrong secret → 401), and dedup (running it twice sends zero duplicate reminders). 27/27 assertions passed. `npm run build`, `tsc --noEmit`, and `eslint` all clean. All test users/checks/properties/storage objects/audit rows/notifications deleted afterward — confirmed zero leftover `phase7-*` rows.

## Working agreement

- Build and verify one phase at a time — each phase should be testable against the real Supabase project before starting the next.
- Any change to `checks.status` must go through an existing (or new) `SECURITY DEFINER` RPC, never a direct client `UPDATE` — this is the load-bearing assumption behind the RLS model.
- New document types or visibility rules require updating both the `documents` RLS policies **and** the mirrored `storage.objects` policies in the same migration.
